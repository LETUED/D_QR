# 1. 왜 QR 원리를 먼저 알아야 하는가

## 1.1 혁신의 출발점

D_QR 프로젝트의 목표는 QR 코드를 "다차원으로 확장"하는 것이다. 그러나 무엇을 확장하는지 정확히 알지 못하면 어디서 혁신해야 할지 모른다.

딥러닝에서 새로운 아키텍처를 설계하려면 기존 모델의 수학적 기반을 먼저 이해해야 하듯이, D_QR도 QR의 정확한 인코딩 메커니즘을 이해해야 한다.

## 1.2 핵심 질문

이 문서가 답해야 할 핵심 질문:

```
QR 코드의 각 "모듈(Module)"에는 왜 1비트만 담기는가?
→ 이 제약을 깨는 것이 D_QR의 출발점이다.
```

# 2. 1D 바코드 — 선형 인코딩의 구조

## 2.1 기본 원리

**모듈(Module)** = 가장 가는 바의 너비 (X-dimension).  
모든 바와 공백의 너비는 이 X-dimension의 정수 배다.

```
| 1x | 2x | 3x | 1x | 2x |
  ■■  □□□□  ■■■■■■  □□  ■■■■
```

- 검정 바(Bar) + 흰 공백(Space)의 **너비 비율** = 데이터
- 패턴을 문자 룩업 테이블과 대조 → 데이터 복원

## 2.2 읽기 메커니즘

```
레이저/LED 발사
      ↓
바(Bar) → 빛 흡수 → 전기 신호 낮음
공백(Space) → 빛 반사 → 전기 신호 높음
      ↓
아날로그 파형 → 너비 측정 (시간 × 스캔 속도)
      ↓
너비 비율 → 룩업 테이블 → 문자 데이터
```

## 2.3 Code 128의 구조

- 각 문자 = 6요소 (바 3개 + 공백 3개) = 11모듈
- EAN-13: 13자리 숫자 → 113모듈 (완전 고정)
- 패리티: 바 너비 합 = 항상 짝수, 공백 너비 합 = 항상 홀수 (자기 검증)

## 2.4 1D의 근본적 한계

```
용량 ∝ 물리적 길이
```

더 많은 데이터 = 더 긴 바코드. 넓이 방향은 완전히 낭비된다.  
이 낭비를 활용한 것이 2D 코드의 출발점이다.

# 3. 2D QR 코드 전체 구조 분해

## 3.1 Version과 크기

QR은 Version 1 ~ Version 40까지 존재한다.

| Version | 모듈 크기 | 총 모듈 수 | 최대 용량 (ECC-L) |
|---------|---------|----------|-----------------|
| 1 | 21×21 | 441 | 41 bytes |
| 5 | 37×37 | 1,369 | 154 bytes |
| 10 | 57×57 | 3,249 | 470 bytes |
| 20 | 97×97 | 9,409 | 1,171 bytes |
| 40 | 177×177 | 31,329 | **2,953 bytes** |

## 3.2 구조 요소별 모듈 소비 (Version 1 기준)

```
┌─────────────────────────────────┐
│ ▓▓▓▓▓▓▓       ▓▓▓▓▓▓▓          │  ← 파인더 패턴 (좌상)
│ ▓     ▓       ▓     ▓          │
│ ▓ ▓▓▓ ▓  타이밍  ▓ ▓▓▓ ▓    │
│ ▓ ▓▓▓ ▓ ─────── ▓ ▓▓▓ ▓    │
│ ▓     ▓         ▓     ▓        │
│ ▓▓▓▓▓▓▓         ▓▓▓▓▓▓▓        │
│         포맷정보                 │
│    데이터 모듈 영역               │
│ (사문형 경로로 비트 배치됨)        │
│ ▓▓▓▓▓▓▓                        │
│ ▓     ▓                        │  ← 파인더 패턴 (좌하)
│ ▓ ▓▓▓ ▓                        │
│ ▓     ▓                        │
│ ▓▓▓▓▓▓▓                        │
└─────────────────────────────────┘
```

| 구성 요소 | 역할 | Version 1 모듈 수 | 비율 |
|----------|------|-----------------|------|
| 파인더 패턴 3개 | 위치/방향 감지 | 3 × (7×7) = 147 | 33% |
| 구분자 | 파인더-데이터 경계 | ~48 | 11% |
| 타이밍 패턴 | 격자 스케일 자 | ~26 | 6% |
| 포맷 정보 | 마스크 + ECC 레벨 | 31 | 7% |
| **데이터 모듈** | **실제 정보** | **208** | **47%** |

> **핵심 인사이트:** Version 1 기준 **53%가 기능 패턴 오버헤드**다.  
> Version이 커질수록 이 비율은 낮아진다 (더 효율적).

# 4. 파인더 패턴과 방향 감지의 수학

## 4.1 1:1:3:1:1 비율의 비밀

파인더 패턴은 7모듈 너비의 동심원 구조다:

```
■ □ ■ ■ ■ □ ■
```

스캐너가 이 패턴을 통과할 때 비율 = 1:1:3:1:1  
이 비율은 QR 코드 외부의 자연 이미지에서 발생할 확률이 매우 낮다.

**핵심:** 어느 방향(0°, 45°, 90°, 135°, 180° ...)으로 읽어도 같은 1:1:3:1:1 비율이 나온다.  
→ **회전 불변(rotation-invariant) 위치 감지** 가능.

## 4.2 세 개의 파인더로 방향 결정

```
[FP1]───────[FP2]
  |               
  |               
[FP3]            
```

- 세 파인더 패턴의 상대 위치로 코드의 방향(0°/90°/180°/270°) 결정
- 네 번째 코너에 파인더 없음 → 비대칭으로 방향 구분

## 4.3 정렬 패턴 (Version 2+)

Version이 크면 인쇄/촬영 시 원근 왜곡이 심해진다.  
정렬 패턴(5×5)을 격자 곳곳에 배치해 호모그래피 보정:

```
실제 이미지 좌표 → 호모그래피 행렬 H → 정규화된 격자 좌표
```

# 5. 데이터 인코딩 4가지 모드

## 5.1 모드별 효율

각 세그먼트 시작에 **4비트 모드 지시자** + 문자 수 지시자:

| 모드 | 대상 문자 | 인코딩 효율 | 최대 용량 (v40-L) |
|------|----------|-----------|-----------------|
| Numeric | 0~9 | 10비트 → 3자리 (3.33 b/char) | 7,089자 |
| Alphanumeric | 0~9, A~Z, $%*+-./: | 11비트 → 2자리 (5.5 b/char) | 4,296자 |
| Byte (UTF-8) | 전체 ASCII/UTF-8 | 8비트 → 1바이트 | **2,953바이트** |
| Kanji | Shift JIS 한자 | 13비트 → 1자 | 1,817자 |

## 5.2 인코딩 예시

`"123"` → Numeric 모드 → `01111011` (123 = 0b01111011, 10비트로 표현)  
`"AB"` → Alphanumeric → `0b00111100101` (A=10, B=11 → 10×45+11=461 → 11비트)

# 6. Reed-Solomon 오류정정의 수학

## 6.1 왜 QR이 30% 손상에도 읽히는가

Reed-Solomon(RS) 코드는 GF(2⁸) = GF(256) 위의 다항식 연산에 기반한다.

**기본 아이디어:** 데이터를 다항식의 계수로 보고, 그 다항식을 여러 점에서 평가한 값을 함께 전송. 일부 값이 손상되어도 다항식을 복원 가능.

## 6.2 인코딩 과정

```
1. 데이터 다항식: d(x) = d_{k-1}x^{k-1} + ... + d_1x + d_0

2. 생성 다항식: g(x) = (x - α¹)(x - α²)···(x - α^{2t})
   (α = GF(256)의 원시원소, α = 0x02)
   (t = 복구 가능한 오류 수)

3. ECC 코드워드: r(x) = d(x) · x^{2t} mod g(x)

4. 전송: c(x) = d(x) · x^{2t} - r(x)
   → c(x)는 g(x)의 배수 (모든 근 α^i에서 c(α^i) = 0)
```

## 6.3 디코딩 과정 (오류 복원)

```
수신: r(x) = c(x) + e(x)  (e = 오류)

1. 증후군 계산: S_j = r(α^j) = e(α^j)  (j=1~2t)
   → S_j ≠ 0 이면 오류 발생

2. Berlekamp-Massey 알고리즘으로 오류 위치 다항식 σ(x) 계산
   → σ(α^{-i}) = 0 ↔ 위치 i에 오류

3. Forney 공식으로 오류 값 계산:
   e_j = -Ω(X_j) / σ'(X_j)
   (Ω = 오류 평가 다항식, X_j = α^{위치})

4. r(x) - e(x) = c(x)  → 원본 복원
```

## 6.4 ECC 레벨별 복구 한계

| 레벨 | 복구 가능 손상 비율 | 용량 사용 비율 | 사용 사례 |
|------|------------------|-------------|---------|
| L | ~7% | 가장 적음 | 스캔 환경 좋을 때 |
| M | ~15% | 중간 | 일반적 |
| Q | ~25% | 큼 | 공장/야외 |
| H | **~30%** | 가장 큼 | 로고 삽입 QR |

> 로고가 삽입된 QR이 읽히는 이유: ECC-H 레벨로 손상된 부분을 복원하기 때문이다.

# 7. 마스킹 — 왜 데이터를 뒤섞는가

## 7.1 마스킹의 필요성

데이터를 그냥 배치하면 파인더 패턴(1:1:3:1:1)과 유사한 패턴이 데이터 영역에 우연히 생길 수 있다. → 스캐너 오검출.

해결책: 데이터 전체에 마스크 패턴을 XOR 적용해 이를 파괴.

## 7.2 8개 마스크 패턴

i=행, j=열 (0부터 시작):

| 패턴 번호 | 수식 | 효과 |
|---------|------|------|
| 0 | (i+j) mod 2 = 0 | 체스판 |
| 1 | i mod 2 = 0 | 수평 줄무늬 |
| 2 | j mod 3 = 0 | 수직 줄무늬 |
| 3 | (i+j) mod 3 = 0 | 대각 패턴 |
| 4 | (⌊i/2⌋+⌊j/3⌋) mod 2 = 0 | 2×3 블록 |
| 5 | (i·j) mod 2 + (i·j) mod 3 = 0 | 복합 |
| 6 | ((i·j) mod 2 + (i·j) mod 3) mod 2 = 0 | 복합 |
| 7 | ((i+j) mod 2 + (i·j) mod 3) mod 2 = 0 | 복합 |

## 7.3 최적 마스크 선택 — 페널티 함수

8개 마스크 모두 적용해보고 **페널티 점수 최소**인 것 선택:

| 규칙 | 패널티 | 대상 패턴 |
|------|-------|---------|
| 규칙 1 | +3 (5개 연속 동색) | 파인더 유사 방지 |
| 규칙 2 | +3 (2×2 동색 블록) | 균일성 파괴 |
| 규칙 3 | **+40** (1:1:3:1:1 패턴) | 파인더 오검출 방지 |
| 규칙 4 | 흑 비율 50% 편차 × 2 | 균등 분포 유도 |

> 규칙 3의 +40은 압도적으로 크다. 파인더 패턴 닮은 것이 생기면 무조건 다른 마스크 선택.

# 8. 데이터 배치 경로 (사문형 경로)

## 8.1 배치 방식

데이터 모듈을 **2컬럼 단위** 지그재그로 배치:

```
방향: ↑ (아래서 위)
      ↓ (위서 아래)
번갈아 가며 전진

→ → ↑ ↑ ← ← ↑ ↑ → →
          ↕         ↕
← ← ↓ ↓ → → ↓ ↓ ← ←
```

- 최상위 비트(MSB)가 오른쪽에 배치됨
- 파인더/타이밍/정렬 패턴은 건너뜀

## 8.2 배치 순서의 의미

데이터가 특정 공간적 패턴 없이 분산되기 때문에:
- 국소 손상 → RS 오류정정이 효과적으로 작동
- 연속된 비트가 물리적으로 흩어짐 → 버스트 오류에 강함

# 9. 색상 QR (JAB Code) — 첫 번째 차원 추가

## 9.1 색상 알파벳

8색 팔레트(2³=8) → **모듈당 3비트**:

```
색상 0: 검정  (000)
색상 1: 흰색  (001)
색상 2: 빨강  (010)
색상 3: 파랑  (011)
색상 4: 노랑  (100)
색상 5: 초록  (101)
색상 6: 보라  (110)
색상 7: 주황  (111)
```

색상 선택 기준: HSV 색 공간에서 최대한 균등하게 분리 (색상 혼동 최소화).

## 9.2 디코딩 파이프라인

```
카메라 캡처 → RGB 이미지
     ↓
호모그래피 보정 (기울기/원근)
     ↓
각 모듈 중심 픽셀 RGB 추출
     ↓
RGB → HSV 변환
     ↓
최근접 색상 팔레트 매핑 (L2 거리)
     ↓
8색 → 3비트 역매핑
```

## 9.3 JAB Code의 현실적 한계

| 이론 용량 | 실제 용량 | 원인 |
|---------|---------|------|
| QR의 3배 | QR의 ~2.5배 | 색상 분리 오류 |

**색상 오류 원인:**

1. **조명 조건**: 형광등/햇빛/LED에 따라 색조 이동
2. **인쇄 CMYK → RGB**: 색 gamut 변환 손실  
3. **카메라 화이트 밸런스**: 자동 보정이 색 데이터 왜곡
4. **채널 크로스토크**: CMYK 잉크 혼합 시 의도치 않은 색 생성
5. **모듈 크기 vs 색 분리**: 모듈이 작아질수록 인접 색이 번짐

# 10. QR이 1비트/모듈에 머문 이유 (핵심 병목)

## 10.1 역사적 제약 (1994년)

QR 코드는 1994년 덴소 웨이브가 자동차 부품 추적용으로 개발했다.

```
1994년 기술 환경:
- 카메라: CCD, 흑백 레이저 스캐너가 표준
- 인쇄: 흑백이 기본, 컬러 인쇄는 고가
- 처리: 임베디드 마이크로프로세서 → 연산 제약
```

이진(흑/백)만 사용한 것은 당시 **스캐너 기술의 한계**이자 **보편성 우선** 설계 결정이었다.

## 10.2 표준화의 굳어짐

ISO 18004로 표준화된 후:
- 수억 대의 기존 스캐너가 흑백 기반
- 새로운 포맷은 호환성 파괴
- 표준 변경 비용이 너무 큼

## 10.3 ECC 설계의 최적화 방향

기존 Reed-Solomon이 GF(256) 이진 필드에서 최적화됨.  
색상이나 다중 값을 다루려면 GF(q) 확장 필드로 ECC를 재설계해야 함 → 추가 연구 필요.

## 10.4 D_QR에 주는 핵심 시사점

```
QR이 1비트/모듈에 갇힌 이유:
1. 1994년 기술 제약 → 지금은 없음 (스마트폰 카메라, 컬러 디스플레이)
2. 보편적 스캐너 호환 → D_QR은 전용 앱 디코더 허용
3. 단일 채널 ECC → 채널별 독립 ECC로 확장 가능
4. 이진 마스킹 → 다차원 마스킹으로 재설계 가능

이 4개 제약을 제거하면 → D_QR의 설계 공간이 열린다
```

# 12. D_QR 프로젝트와의 연결

## 12.1 QR 구조에서 차용할 것

| QR 요소 | D_QR 적용 |
|---------|---------|
| 파인더 패턴 3개 | 재사용 (방향 감지는 동일하게 필요) |
| 타이밍 패턴 | 재사용 또는 개선 |
| 정렬 패턴 | 재사용 |
| 사문형 데이터 배치 | 다차원 텐서 배치로 확장 |
| Reed-Solomon ECC | 채널별 독립 RS로 확장 |

## 12.2 QR에서 버릴 것 (D_QR의 혁신 지점)

| QR 제약 | D_QR 해결책 |
|---------|-----------|
| 흑/백 이진 (1비트/모듈) | HSV 다채널 (최소 5비트/모듈) |
| 단일 마스킹 (8개 패턴) | 차원별 독립 마스킹 |
| 단일 스트림 ECC | 채널별 우선순위 ECC |
| 레이저 스캐너 기반 | 스마트폰 카메라 + AI 디코더 |

## 12.3 단계적 확장 비전

```
QR (1비트/모듈, 흑백)
        ↓
JAB Code (3비트/모듈, 8색)
        ↓
D_QR Phase 1 (5~7비트/모듈, 색상 3채널)
        ↓
D_QR Phase 2 (+패턴 차원, 10~12비트/모듈)
        ↓
D_QR Phase 3 (+주파수 도메인, 14~15비트/모듈)
        ↓
Neural D_QR (신경망 인코더/디코더, 이론 한계 탐색)
```
